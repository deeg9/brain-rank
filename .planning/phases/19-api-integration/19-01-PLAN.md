Create `web/src/app/api/jobs/[id]/route.ts` with a named export `GET`:

```typescript
import { NextRequest, NextResponse } from 'next/server'
import { createClient } from '@/lib/supabase/server'
```

The GET handler receives `{ params }: { params: Promise<{ id: string }> }` as the second argument (Next.js 15 async params pattern).

The handler must:
a. Await params to get `id`. Call `createClient()`.
b. Call `supabase.auth.getUser()` -- if no user, return 401.
c. Fetch the job: `supabase.from('jobs').select('*').eq('id', id).single()`. If not found, return 404 with `{ error: 'Job not found' }`.
d. Verify `job.user_id === user.id` -- if mismatch, return 404 (do NOT return 403 to avoid leaking job existence).
e. If job.status is `'completed'` or `'failed'`, return the job as-is (no need to poll RunPod).
f. If job.runpod_id is null (RunPod never started), return the job as-is with its current status.
g. Otherwise, poll RunPod: `fetch(\`https://api.runpod.ai/v2/${endpointId}/status/${job.runpod_id}\`, { headers: { 'Authorization': \`Bearer ${apiKey}\` } })`.
h. Parse RunPod response. Map RunPod status to job status:
   - `"IN_QUEUE"` or `"IN_PROGRESS"` -> `'processing'`
   - `"COMPLETED"` -> `'completed'`
   - `"FAILED"` or `"CANCELLED"` or `"TIMED_OUT"` -> `'failed'`
i. Build an update object. Always set `status`. If RunPod status is `"COMPLETED"` and `output` exists, set `results: runpodResponse.output`. If RunPod status is `"FAILED"`, set `error_message: runpodResponse.error || 'Inference failed'`.
j. Update the job in Supabase: `supabase.from('jobs').update(updateData).eq('id', id).select().single()`.
k. Return `NextResponse.json(updatedJob)`.

If the RunPod fetch itself fails (network error), do NOT update the job status -- just return the current job as-is with a warning field: `{ ...job, _polling_error: 'Could not reach RunPod' }`. This avoids falsely marking a job as failed due to a transient network issue.

Wrap in try/catch, return 500 on unexpected errors.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser -> API routes | Untrusted input (video_url, job id) crosses here |
| API routes -> RunPod | Server-to-server, API key in Authorization header |
| API routes -> Supabase | Server-to-server, auth via session cookie forwarding |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-19-03 | Information Disclosure | GET /api/jobs/[id] | mitigate | Return 404 (not 403) when job belongs to different user -- prevents enumeration |
| T-19-04 | Information Disclosure | Both routes | mitigate | RUNPOD_API_KEY only in server-side process.env, never in NEXT_PUBLIC_ or response bodies |
| T-19-05 | Tampering | POST /api/jobs | mitigate | Validate video_url starts with http(s):// before passing to RunPod |
| T-19-06 | Denial of Service | POST /api/jobs | accept | No rate limiting in v2.0 (deferred per CONTEXT.md). Auth requirement provides basic protection. |
